# Shared: voice, plain words, style guide and glossary

## 1. When to read this
Every call, in every mode, before writing a line.

## 2. Plain words
- Short sentences, common words, one idea per sentence.
- Use the reader's own words, not the team's internal names. Explain a needed technical word once, in a few words.
- Main point first. The first line of a store page, a post, a help answer or a README must do the most work.
- Fit the reading level to the reader. A player or a new user gets everyday words; a developer page may use the exact technical term.
- English only (owner decision Q31). Every file is English, even when the chat is in another language.
- The base rules are in `hire-an-engineer/references/plain-language.md`; follow them, do not copy them.

## 3. Voice and tone
- **Voice** is how the product always sounds. **Tone** changes with the moment: a launch post is not a refund reply.
- Set tone on four scales and write the setting down: formal or casual, serious or funny, respectful or cheeky, matter-of-fact or excited.
- Support tone: calm, warm and clear, never cheeky or salesy. Docs tone: matter-of-fact. Marketing tone must not leak into support replies or docs.

## 4. The style guide (`docs/writing/style-guide.md`)
- Holds: the voice, the tone setting per situation (store, ads, posts, docs, support), words to use and avoid, product names, how numbers, dates and times are written.
- If the project has none, draft a short one from the brief and the existing product text, and mark every line `draft`.
- Each line is `draft` or `approved`, with a date and who approved it. Only the owner (or the person the owner names) makes a line `approved`.
- The owner's own style guide wins over any outside guide.

## 5. The glossary (`docs/writing/glossary.md`)
- One approved word for each thing (for example "coins", never also "gold" and "money" for the same thing).
- Line shape: `term | meaning in plain words | words not to use for it | status (draft or approved) | date | approved by`.
- All four modes use the same glossary. A new term is added as `draft` and listed in the answer for approval.
- A glossary term is reused many times, so one wrong term spreads everywhere. When the product changes, list the lines that may be stale; you do not wake yourself, a stale line is found when the boss calls you.

## 6. Versions
When a brief asks for options, write versions that change one thing each (the first line, the hook, the ending, the length), and name each version so results can be read against it later. You do not say which one will win; only a test shows that.
